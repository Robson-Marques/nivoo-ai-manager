# Adoção integral e evidência

Adoção não é copiar arquivos nem aplicar uma aparência isolada. O modelo Studio Workflow permanece a autoridade para piloto, propagação e coexistência. O contrato usa critérios de Capability existentes: structural traz config.adoption, acceptance declara adoptionFamilies e decision exige decisão humana. Um piloto ou rollout com pendências é uma etapa concluída, não uma adoção integral. O inventário mapeia famílias e callsites reais; a aceitação existente emite evidência por cenário executado. O Nivoo valida o mapa, a integridade do pacote oficial Liqui Design e a presença de imports relativos nos callsites declarados. Isso não prova que todo callsite foi enumerado, que o código foi usado em todos os estados nem a fidelidade estética: os testes e a decisão humana permanecem indispensáveis.

O backend exige o contrato nos planos de adoção explicitamente reconhecíveis pelo título/objetivo e nas entregas integradas de interface (Capability) com Liquid Glass selecionado. Não tenta inferir universalmente todas as tecnologias em qualquer código ou reinterpretar trabalhos já aprovados. Outras bibliotecas/metodologias podem usar o mesmo contrato; a validação binária de fontes e componentes é específica do Liqui Design. Não há nova sessão de revisão, CI, tabela ou fila.

O pacote de design entrega os 38 componentes do registry fixado, com apenas os imports internos ligados ao engine local. O projeto consumidor instala as dependências pertinentes e configura Tailwind v4, importa componentes oficiais e preserva seus arquivos. Uma incompatibilidade de stack deve ser resolvida antes de confirmar a adoção, não substituída por CSS inventado. Os projetos existentes não são reescritos automaticamente.
